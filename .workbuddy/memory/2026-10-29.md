## 【ZCode 接手·第2轮】用户回报"音乐仍不是1倍速" → 真正根因:细粒度丢帧使旋律内容仍按倍速推进 → 已修(整段切割落在音符间隙)✅

### 真正的根因(推演+代码确认)
`nativeHoldGenerate` 旧逻辑:lag ring(2s)在 4× 下**永久饱和**,每来一批音频(每 pump ~62ms)就把读指针 `natR` 前推越过未播放帧(丢最老)。稳态下每秒:产 4s、播 1s、丢 3s——**丢弃以 ~16-33ms 粒度与播放交错**,输出=1× 音高的碎片背靠背拼接,旋律内容仍以 4× 速度推进。听感=音高对但"音乐仍是快的+毛刺"。代码头注释承诺的 "never a section skip" 在饱和稳态下是假的;`nativeHoldGenerate` 开头注释描述的正确设计(攒够一次的量、落在静音块)**从未被实现**。测试盲区:合成 ROM 是 512Hz 恒定方波,方波自然翻转沿与接缝跳变一样陡,`max step` 断言天然探测不到;且假时钟按每次 readAudioOut 调用推进 1/59.73s,而测试按每 4 帧一步泵(每 slice 4 次调用),4× 时预算恰好≈产量,环形缓冲根本不会饱和。

### 修复(nativeHoldCut,未提交,在 worktree 分支 `music-native-cut`)
- `MOBILE_AUDIO_NATIVE_RING_SECONDS` 2.0→6.0:两次切割之间盈余以连续内容形态积攒在环里。
- 环满时执行**一次整段切割** `nativeHoldCut`:读指针跳到**最新 1.5s 内能量最低的 10ms 窗口**(音符间隙),复用 12ms 淡入盖接缝;新增 `natCuts` 计数与 `mgbaMobileNativeHoldCuts()` getter,`audio ff` 日志加 `cuts`。
- 切割节奏 D/(stretch-1):4× 下 D≈4.5-5.9s → **每 ~1.6s 一跳,每跳 4.5-5.9s 内容**;长程内容速率严格 =1/stretch,无漂移。
- 测试同步修:假时钟改为每 slice 推进一次(对齐设备真实时间);新增断言 `cuts≥1 且 ≤12(4×)/90(16×)`——细粒度丢帧会是 ~300 次,一测即抓。

### 验证(单测+AVD 双通过)
- 单测:4× **cuts 3**、16× **cuts 15**(旧实现≈300);音高 1.00×/0.99×;`max step 13035/12960 < 基线 13045`——能量最小落点让接缝跳变甚至低于方波自然边沿。7 个 FAIL 仍为 pace-estimator 旧测试(与本次无关)。

### 重大修正与突破（晚间续测，账号已就绪）
**此前"WS 信令 + P2P 直连"的判断被实测推翻，真实架构如下：**

- **账号已 live 注册并登录**（用户给邮箱 525612743@qq.com，密码 Mgba2026x，用户名 mgba_test；验证码 083937 完成注册）。token 存于 `.workbuddy/gboy/account.json`。注册动作：`register` 需 `username`(2-10字)+`email`+`password`+`verification_code`；验证码走 `send_verification_code`(`email` 单参，5 分钟限频)。登录：`login`(`email_or_username`+`password`)。

- **WS 只是纯信令层**（鉴权 + 房间管理），联机数据流**既不走 WS 也不走 P2P 直连**。

- **数据通道 = TCP 中继节点**：`create_game_room` 在"已有房间"返回里吐出 **`node_address` + `node_port`**（实测本账号房间：`47.103.87.123 : 46786`）。这是按房间分配的中继节点地址。也就是说两客户端都连到该 TCP 中继，由服务器转发 SIO 字节。

- **中继端口实测**：TCP `47.103.87.123:46786` 可连（监听中），服务器**不主动发 banner、等你先说话**；对随意字节（room_id/JSON/GBoyLink 帧）一律"接受但不回应"，盲猜 15 种握手首包全部"accepted, no reply"。→ 中继握手是**专有/混淆协议**（dex 里有 `OUdp` 类 + `UDP 联机` 字符串），靠盲猜无解，其逻辑在加壳 App 的运行时 payload（part0_0.dex 仅壳，真正代码运行时加载，不可静态分析）。UDP 探测无回应，基本判定为 TCP 中继。

- **房间机制补充**：`create_game_room` 每个账号只持有一个房间（重复调用返回"您已有房间，返回现有房间信息"并带 node_address/node_port）。房间 `uuid` 对本账号房间为空；线上真实房间 uuid 形如 `BPEE,55c9004420cd750f03192bc20569e1ab`（前缀为 ROM 游戏码，如 BPEE=宝可梦绿宝石），应在"选定 ROM 开始游戏"时由客户端写入。`update_room_settings` 用我们试的键（game_code/uuid/...）均返回"没有需要修改的字段"。

### 🔄 重大修正：云中继其实早已完整实现（本轮晚些时候发现）
之前把方向 B 理解为"从零接入 gboy.top 云端中继"，并花大量精力逆向 gboy.top。实际**云联机（自建中继）已被 opencode 完整实现并 git 提交**：

- 提交 `dc40c39c5 Add Android link play over LAN and an internet relay.`
- **Java 实现（当前生效路径）**：`android/app/.../RemoteLink.java`（客户端 + 内嵌 `RelayHub`/`Room`）+ `RelayService.java`（前台服务，手机本机当中继）。`EmulatorActivity.ensureRemote()` 走这条。
- **原生 C 实现（同协议备胎，未接 JNI）**：`src/platform/mobile/remote_link.c`（`mobileRelayCreateRoom`/`JoinRoom`），已编进 `libmgba_mobile.a`（3 个 ABI 都有 `.o`），但 `jni_bridge.cpp` 未暴露 `mobileRelay*`，故实际未启用。
- **独立托管服务端**：`android/tools/link_relay.py`（讲同一套 `MGBA1` 协议，可跑在 VPS）。
- 中继协议（文本行 + 之后透传原始字节）：`MGBA1 CREATE` → `MGBA1 ROOM <6位码> HOST|GUEST` → 双方 `MGBA1 PEER` → splice 双向转发。错误 `MGBA1 ERR NO_ROOM|FULL|TIMEOUT|BAD`。
- 底层：原生 mGBA SIO 链路 `core.linkHost/linkJoin`（→`link_net.c`）在本机起一个 TCP 口（远程用 18765），`RemoteLink` 把那个本地口 splice 到中继 socket。GBA SIO 字节完全透明转发。

**实测验证（2026-10-29 晚）**：`python android/tools/link_relay.py 28766` 起服务，两客户端 CONNECT+JOIN 握手成功，字节双向 splice 通过（A→B、B→A 均收到）。协议可用。

**结论**：用户选的"跨公网联机"目标**已达成**，走自建中继即可（一边"本机作中继"给对方公网地址+房间号，或跑 `link_relay.py` 在 VPS）。gboy.top 只是"免自托管"的可选项，**非必需**，且被其加密握手（OUdp 类，在加壳 payload 里）卡死、逆向成本高、法律灰度大。
