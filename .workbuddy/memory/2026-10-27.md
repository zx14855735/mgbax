### 关键代码事实（mGBA 内核）
- `src/gba/sio.c`：MULTI 模式只有 P1（deviceId==0）写 start 位才会 `_startTransfer`；
  P2（deviceId==1）写 start 被忽略 → P2 的传输完成必须由外部（我们的 `finishIncoming`）驱动，设计方向正确。
- driver->start 返回 false 时 sio.c 不再自行调度完成事件（驱动自己负责完成），这是做网络联机的正路。
- `GBASIOMultiplayerFinishTransfer` 会清 Busy、写 SIOMULTI0..3、按 bit14 触发 SIO IRQ。

### 2026-10-27 下午：找到并修复 MULTI 从机缺陷
- 读 `src/gba/sio.c` 确认：`GBASIOWriteSIOCNT` 里 MULTI 模式下只有 `id==0`（1P）写 start 位会调
  `_startTransfer`，2P..4P 那一支是 `// TODO` —— 从机既没人发起也没人完成，SIOCNT 的 Busy
  位永远不会被清，游戏等到超时就报「通信错误」。这是「大厅连上了但游戏里连不上」的根因。
- 修 `mgba_mobile.c`：
  1. `gbaLinkWriteCnt()` 里检测 MULTI 从机的 Busy 上升沿，调用新增的 `beginMultiRequest()`
     自己发起这次传输（内核不会替它做），返回 false 语义等价于「完成由驱动负责」。
  2. `gbaLinkDevices()` 从 2 改成 1：`connectedDevices` 的语义是「对端数量、不含自己」
     （同 gbp.c）。填 2 会让内核按 3P 的传输周期算，每次传输比真机慢 50%。
  3. `finishIncoming()` 的 MULTI 分支加守卫：本机不在传输中（Busy 位=0）时不收尾，
     避免把上一帧结果覆盖成新数据。
  4. 加统计日志 `SIO multi me=%d ok= last= peak= retry= to= fb=`（每 64 次打印一条，
     MOBILE_LOGI → logcat tag mGBA），排查联机直接看这一行。

### 16:25-16:55 修复 SIO kick + 决定性验证（已解决“大厅连上但游戏连不上”）

- **根因最终确认**：真实 Pokemon 系联机发起 MULTI 传输时写 `0x600F`（IRQ=bit14 置起、Busy=bit7 不置）。
  内核 `GBASIOWriteSIOCNT` 只在 Busy 上升沿（且 id==0/1P）起传输，2P 那一支是 TODO；而 `0x600F` 不置 Busy，
  所以内核永不发起/完成 → Busy 永不落 → 游戏超时报“通信错误”。旧驱动只在 `irqRise`（bit14 第一次上升沿）kick，
  `0x600F` 第二次起 bit14 再无上升沿 → **除第一次外所有传输都触发不了**。
- **修复**（`src/platform/mobile/mgba_mobile.c` `gbaLinkWriteCnt`）：触发条件从 `nowBusy || irqRise`
  改成 `nowBusy || (irq && !emu->sioWaiting)` —— MULTI 模式 + IRQ 置位 + 当前无挂起传输 就 kick，
  配合 `!sioWaiting` 守卫避免同一次传输发起两次。PUSH 通道（双端各自在传输末尾取用对端数据）保持不变。
- **验证**：AVD 极慢（boot 93s、每轮 ~9s），先用自制 `siotest2.gba`（写 0x600F、不置 busy）确认 kick 持续触发
  （`SIO begin idx` 一直递增）。再烧 `siotest3.gba`（精简版，去掉绘图/大延时加速）凑够 64 次完成：
  - A(me=0): `SIO multi me=0 ok=192 to=0 m0=1260 m1=217F`；B(me=1): `SIO multi me=1 ok=192 to=0 m0=1260 m1=217F`。
  - `to=0`（零超时）；两端同一时刻 SIOMULTI 完全一致（P1=0x1xxx/P2=0x2xxx）→ **双向交换正确**；`ok` 持续攀升。
  - 结论：0x600F 现在每次都能发起并完成 MULTI 传输，根因修复得到 SIO 层决定性验证。
