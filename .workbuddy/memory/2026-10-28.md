## 修复：连点B跑步卡死（mGBA Android 模拟器）

**根因**：专用于连发B的屏幕按钮（ControlsView 的 B连/连发键）通过 `publish→onKeysChanged→noteUserKeys→core.setKeys` 把 B 位脉冲进 `heldKeys`；同时 `noteUserKeys` 看到 B 被按住超过 `TURBO_ARM_MS` 又会去 arm 住手B自动连发（`armTurbo`→`core.setTurbo(B)` 设 `turboMask`，并 `publishKeys` 从 `heldKeys` 剥离 B）。结果是 B 同时被两个来源驱动。原生 `readLiveKeys` 里 `keys = frameKeys | held | latch`，`beginFrameKeys/applyTurbo` 在 turbo 关帧已正确撤下 B，但 `held` 仍带有连发按钮的 B 位 → 又被 OR 回去，B 每帧都被报成按下。宝可梦类游戏按住 B=跑步，于是角色一直跑停不下来（“跑步卡死”）。

**修复（两处）**：
1. `src/platform/mobile/mgba_mobile.c` `readLiveKeys`：在合并 `held`/`latch` 前先把 `turboMask` 对应位屏蔽掉，保证 turbo 键只由 `applyTurbo`/`turboMask` 每帧决策控制，关帧不会被 held 重新置位。这是根因修复。
2. `android/.../EmulatorActivity.java` `noteUserKeys`：当 B 的按下来自专用连发按钮（`controls.turboBPressed()`）时，不再 arm 住手B自动连发，避免两套 turbo 叠加。
3. `android/.../ControlsView.java`：新增 `turboBPressed()` 访问器，供上面的 guard 使用。

- **待确认风险**：`D:/gen8/rom.sav` 实际为 131088 字节 = 128KB + 16 字节头部（前 16+ 字节为 0x00，非 mGBA 的 MBSC 魔数；本代码库 grep "MBSC" 为空，说明是较老版本、裸存档无头）。mGBA 裸存档加载（`GBASavedataInitFlash` 直接 `map(vf, flashSize)`）会取文件前 131072 字节当存档，即把那 16 字节零头当存档起始、漏掉末尾 16 字节真实数据 → 理论上可能让宝可梦这类靠校验和的存档整体偏移 16 字节、校验失败。尚未盲改用户存档（怕改错位置损坏）。若用户实测游戏里仍读不到正确进度，再生成「去掉前 16 字节」的干净 131072 字节副本（rom_clean.sav）给他试。

## 修复：倍速时音乐可选「不变速」（mGBA Android）

**需求**：倍速（快进）时音乐应能选「不变速」——保持原速、音高不变，而不是像磁带那样升调。

**关键原理（经核对音频管线确认，此前担心「传 speed=1 仍会升调」是误判）**：
- Android 前端始终以主机帧率（~59.73fps）做节拍（每 slice 跑 factor 帧，`slices++` 一次），故 `pace≈nativeFps` 与倍速无关。
- 原生 `mgbaMobileReadAudioOut` 的 resampler 输入率 `inRate = coreRate * speed / fpsRatio = coreRate * speed * pace/nativeFps ≈ coreRate * speed`（drift≈0）。设备恒以 destRate 实时播放，故**听感音高 = inRate / coreRate = speed**。
- 因此「不变速」= 给 resampler 传 `speed=1`：inRate≈coreRate → 音高正常；快进产生的 `mult-1` 倍多余采样由 resampler 的 low-water-mark consume 丢弃（核心音频环缓冲溢出也只丢多余部分），音乐比画面慢半拍但音高不变。原「磁带式」= 传 `speed=mult`（音高×mult）。

**改动**：
1. `android/.../EmulatorActivity.java`：
   - 新增字段 `appliedGameSpeed`（记录上次配置的 game speed/mult），`setupAudio()` 重置。
   - 重写 `syncFastAudio(double mult)`：正常/慢放→audioSpeed=mult；倍速且「倍速声音」开且「不变速」开→audioSpeed=1.0；否则 tape→audioSpeed=mult；sound 关且倍速→静音。audioSpeed 或 mult 变化都重置音频管线（重新锁 resampler）。
   - `buildSpeedBar()` 在「倍速声音」复选框旁加「不变速」复选框，绑定 pref `fast_audio_const`，且 sound 关时禁用并半透明；两个勾选都触发 `syncFastAudio(currentGameSpeed())`。
   - `pumpAudio` 用 `appliedSpeed` 作为传给 `readAudioOut` 的 rate（既有逻辑，不变）。
2. `android/app/src/main/res/values/strings.xml`：新增 `<string name="speed_sound_const">不变速</string>`。
3. 文档 `android/使用教程.md`、`使用说明.md`：补充「不变速」说明。

## 「不变速」实测结论（重要，推翻了此前的乐观结论）
用户反馈「没效果」。插桩实测（模拟器 + logcat，临时把 speed 固定 4f、constPitch 固定 true，事后已全部还原）：
- `sync mult=4.0 constPitch=true -> audioSpeed=1.0`，`pump rate=1.0` → **speed=1 确实传到了原生层，Java 接线没问题**。
- `buffered` 稳定在 7616~8704，两种模式一致，**没有缓冲失控**。
- 原生实时仿真测试（`testAudioConstPitchRealtime`，忠实模拟 AudioTrack 按 outRate/slicesPerSec 定速消耗）：
  - 1x 基准 512.0 Hz；磁带式 4x = 2048.2 Hz（4.00x）；**不变速 4x = 532.5 Hz（1.04x）** → 音高确实不变。
  - 但输出 241200 帧 / 游戏跑了 1200 帧（20.1 模拟秒）→ **只听到了 5.02 秒的音频，即 3/4 被丢弃**。
- **根因（物理限制，非代码 bug）**：4 倍速时游戏每秒产生 4× 音频采样；要以正常速度播放就只能播放 1/4，剩下 3/4 必须丢弃。丢弃发生在 core 环形缓冲溢出处（零散丢弃）→ 旋律仍以 4 倍速度推进、只是音高不变 → 听感仍是"音乐很快/被切碎"，用户感知为"没效果"。
- 推论：**「不变速」在信号层面是正确的，但物理上无法做到"音乐连续地以正常速度播放"**。可选方案只有：①保持现状（音高正确但旋律碎）；②缓冲后再放（连续但每几百毫秒跳一次，需新增大 FIFO 的原生改动）；③倍速时静音（已有：倍速声音关）；④磁带式升调（现状默认）。已就此询问用户。
- **复用经验**：给 app 插桩 + `adb logcat -s TAG` 是在无 UI 自动化时验证音频链路的有效手段；`run-as` 写 shared_prefs 被拒（can't create），改用"临时硬编码开关 + 重新编译"更可靠。uiautomator 仍无法展开倍速条（菜单 4s 自动隐藏、分辨率每次启动变化）。

## 不变速最终实现：缓冲方案（用户选定）
在重采样器之前加一个大 FIFO（"park"），把多余音频攒起来再以 1 倍速连续播放，攒满时整块丢弃。
- `mgba_mobile.c`：新增 `audioHold`(mAudioBuffer) / `audioHoldScratch` / `audioHoldHigh|Low` / `audioHoldOn|Inited`；新增 `initAudioHold` / `deinitAudioHold` / `parkAudioHold`；`readAudioOut` 在 holdOn 时先 `parkAudioHold` 再把 `source` 指向 park；`clearAudio` 清 park；`deinitAudioOutput` 释放；新增 `mgbaMobileSetAudioConstantPitch()`。
- 常量：`MOBILE_AUDIO_HOLD_SECONDS 5` / `HIGH_SECONDS 4` / `SCRATCH 4096`；low = coreRate/4。
- 链路：`mgba_mobile.h` 声明 → `jni_bridge.cpp` `nativeSetAudioConstantPitch` → `MgbaCore.setAudioConstantPitch` → `EmulatorActivity.syncFastAudio`（`holdSurplus` + 字段 `constantPitchOn`，`setupAudio` 里重置并关闭）。
- **实测（决定性）**：`testAudioConstPitchRealtime` 新增第 4 组 + 新指标 `audioEdgeJitter`（相邻上升沿间隔偏离中位数 >25% 的比例）：
  - 旧（零散丢弃）：音高 1.04x，**jitter 0.101**（切碎）
  - 新（park 后播）：音高 **1.00x**，**jitter 0.001**（连续），约每 1.3s 跳一段
- 原生测试：97 ok / 7 FAIL（**与改动前完全相同的既有 pace 估算器失败，无回归**）。
- 文档已更新：说明音乐会连续按原速播放、每隔约一秒跳一段（倍速越高越频繁）。
- APK 已验证：3 个 ABI 的 .so 均含 `mgbaMobileSetAudioConstantPitch`，dex 含 `setAudioConstantPitch`/`nativeSetAudioConstantPitch`/`constantPitchOn`，arsc 含「不变速」。

## 不变速「跳一段」bug 修复（最终方案：WSOLA 时间拉伸）
- 根因：park 方案把多余音频攒在环形缓冲，填满(约1.3s)就从队首丢弃一整块 → 音乐整段跳。物理上 4x 时产生 4x 音频只能播 1x，丢弃 3/4 不可避免，park 只是把丢弃集中成「跳段」。
- 正确解法：**WSOLA 时间拉伸**（保音高、压缩时长）。在 `mgba_mobile.c` 用 `wsolaIn`(输入队列)+`audioHold`(输出) 取代原 park；分析窗在输入上滑移、用互相关对齐相位、Hann 窗 overlap-add，分析跳 Ha=N/2、合成跳 Hs=N/(2×stretch) → 输出/输入=N/(2s)，多余音频被**压缩**而非丢弃，故无跳段、音高不变。
- 改动文件：`mgba_mobile.c`(wsolaFeed/wsolaGenerate/initAudioHold/deinitAudioHold + readAudioOut 调用 + SetAudioConstantPitch 加 stretch 参数)、`mgba_mobile.h`、`jni_bridge.cpp`、`MgbaCore.java`(setAudioConstantPitch(on,stretch))、`EmulatorActivity.java`(syncFastAudio 传 mult 作 stretch，速度变化实时同步)。
- 原生实测（mobile_test）：WSOLA 4x → 514.3Hz(1.00x 音高)，整曲连续播放(210926/241200)，jitter 0.057（远优于切碎 0.101）。7 个 FAIL 为改动前既有的 pace 估算器用例，无回归。
- 搜索参数经验：tol=Ha/2、step=8 最稳；改细(tol=96,step=1)反而 jitter 0.598 崩坏（窄搜索锁到错误谐波）。
- 文档「跳一段」描述已改为「WSOLA 连续、不跳段」。
- 构建：assembleDebug + assembleRelease 均 BUILD SUCCESSFUL；3 ABI 的 .so 含新符号、dex 含新接线。
