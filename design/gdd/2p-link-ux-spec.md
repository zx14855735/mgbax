## 0. 口径声明（先读）

1. **架构不推翻，只做设计侧适配**。本文件接受已拍板的技术终态：2P 首选 **path A**（每端 1 核 + SIO 包中继，P2P 直连优先）；备选 **path B**（本机 4 核 + 网络只传按键，对外 2P 实为「2 真人 + 2 NPC 占位」的 4 人房，两端各跑一局）；**type 1 握手加 1 bit `mode`（A/B），两端不一致直接 fail 并给玩家可见提示，禁止静默降级**；iOS 无 path A，默认 2P 仅 PC↔Android 可用。
2. **「双人联机」的产品定义不变**：两台设备、两个真人、各玩各的画面、游戏内联机走模拟器联机线；主路径是云端房间 2P；2 人局域网无界面，只能 ADB 广播（`安卓版完整使用教程.md:74,98`）。本文件不改变这个定义，只把实现造成的偏离**如实翻译成玩家可见语言**。
3. **区分两种「降级」，不得混为一谈**（对齐 T-06 §4.5 口径）：
   - **架构级降级**（path A ↔ path B 切换）＝**显式 A/B 不一致永远 fail，无任何切换**；唯一合法回落是「对端未声明 + `MGBAX_LINK_ALLOW_LEGACY=1` / `allow_legacy=true` 显式许可」，且状态栏带「警告…显式许可回落」（§2.1 F5/F6、§5.4）。设计侧另给「双端确认 + 落差告知卡」的**后续产品化建议**，但明确标注为未落地（§5.4）。
   - **通道级回退**（P2P 直连打不通 → UDP 中继 / 服务器隧道）＝设计内允许自动发生，但**必须玩家可见**，且帧率变化必须回显（4.6~4.9 fps）。教程原句「打不通不报错，继续用隧道」在本冲刺起不再成立。
4. **不臆造数据**。帧率、通道、崩溃、真机结论均引自上面「依据」；凡未有落盘证据者标 `[需真机验证]`，不作已实现陈述。
5. `design/accessibility-requirements.md` 与 `design/art/art-bible.md` 在本仓尚不存在（本轮已核查 `design/` 为空）。§9 按通用可访问性基线给出，缺失的正式可访问性需求文档列为待补项，不在本轮补写。

## 1. 设计支柱（Design Pillars）与红线

三条支柱贯穿全部 UX 决策，任何文案/控件若违反即标注为「支柱漂移」：

| # | 支柱 | 一句话 | 可判定条件 |
| --- | --- | --- | --- |
| **P1** | **两个真人，各自一台** | 绝不把 NPC 占位冒充真人玩家；任何偏离「1v1 真人」的形态必须进房前明示 | 玩家在按下「开始/加入」前，能读到本局真实参与构成（真人数量、NPC 数量） |
| **P2** | **状态诚实** | 能力、通道、帧率的每一次变化都可见；宁可显式失败，也不静默降级、不假装成功 | 不存在任何「自动切换模式且不告知」的路径；通道回退后状态栏文案必变 |
| **P3** | **进度隔离** | 联机不得覆盖玩家屏幕上的进度；复位是唯一联动动作且需可知 | 连上/断线/失败任一路径后，本机可见核进度不变；复位前有明确语义说明 |

**红线（来自历史事故，不得突破）**
- 两套帧格式同流曾导致 **9470 个碎片包耗死读线程**（`CloudLink.cpp:608-610`；`MEMORY.md:25`）。⇒ `mode` 不一致必须 fail，**禁止热切换帧格式**。
- path A 里发整份 savestate 会破坏 20 字节 SIO 帧边界（`2026-11-15.md:143-149,196-201`）。⇒ 「互发即时存档」不是全模式承诺，见阶段 4 与 §8.1 M-6，逐句改写见 scope-review §4 承诺 d。
- 跨公网帧锁步每轮 1 RTT、gen8 9 轮/帧 ≈ **0.7~1.5 fps 物理不可行**（`GBoy联机实现拆解与移植方案.md:305-318`）。⇒ 不得向玩家提供「公网 1v1 对战已可用」的暗示。

## 3. 玩家旅程（8 阶段）

> 每阶段按「玩家看到什么 / 能操作什么 / 系统反馈什么」三段写；末尾给状态标注。
> 主路径 = **云端房间 2P（path A）**；path B 差异在阶段内以 `【path B 分支】` 单列。

### 阶段 1 · 启动
- **看到**：`File → 联机大厅…`（PC，`PC版完整使用教程.md:76`）／菜单栏 **联机** 上半部分（Android，`安卓版完整使用教程.md:74-75`）；`[已实现]` **PC 大厅「联机模式：」下拉框**（`AUTO（2P→A / 3·4P→B）` / `A：每端 1 核 + SIO 包中继` / `B：本机多核 + 网络只传按键`，`LobbyView.cpp:96-117`）；`[本冲刺待实现]` 入口旁一个只读模式徽标「双人直连 / 兼容模式（实验性）」与一行平台提示「当前 2P 仅 PC ↔ Android 可用，iOS 暂不支持双人联机」。
- **能操作**：载入 ROM；打开/关闭联机面板；`[已实现]` 在 **PC** 下拉框显式选 A / B / AUTO（持久化 QSettings `link_mode`）；**Android 仅 ADB `GBOY_LINK_MODE --es mode A|B` 可达，无 UI 复选框**（写入 SharedPreferences `gboy_link_mode`，§2.1 F2/F3）；`[本冲刺待实现]` 点模式徽标展开「当前模式说明」（只读）。
- **系统反馈**：未载入 ROM 时禁用「创建/加入」并提示「请先打开游戏」；`[本冲刺待实现]` 面板顶部一条**预防性黄条**：「两端需使用同一种联机模式，否则连接会被安全拒绝」。~~若本机模式与默认组合可能不一致（PC 默认 A / Android 默认 B）~~ —— 该前提已被 AUTO 默认（F1）消除，黄条改为通用的「两端同模式」提示。
- **状态**：入口/ROM 校验 / PC 模式下拉框 / Android 模式入口 `[已实现]`；模式徽标 / 平台提示 / 预防性黄条 `[本冲刺待实现]`。
- **支柱**：P2（事前披露，避免进房才失败）。

### 阶段 2 · 登录 / 建房或加入
- **看到**：邮箱 + 密码（老账号）／邮箱 + 验证码 + 密码（新账号，全程不收邮件）；「云端创建（我是 1P，拿房号）」／「云端加入（填对端房号）」；状态栏「房间已创建，房号 …」（`安卓版完整使用教程.md:78-80`）。
- **能操作**：注册/登录、创建/加入、把房号发给对端；`[本冲刺待实现]` 建房时勾选「本局参与构成」——默认且唯一推荐「2 真人直连」，`【path B 分支】` 需显式选择「兼容模式（实验性）· 2 真人 + 2 电脑占位」并二次确认（见 §6.4）。
- **系统反馈**：房号生成；登录失效（同账号互踢，`MEMORY.md:50-51`）、「房间不存在」（房主重启过 app，`MEMORY.md:59-60`）、「两边的游戏不一致」（ROM 指纹不同，`PC版完整使用教程.md:210`）分别给独立文案，禁止合并成一句「连接失败」。
- **状态**：登录/建房/加入/三条既有错误提示 `[已实现]`；构成选择 + path B 二次确认 `[本冲刺待实现]`；「同 ROM md5 撞 game uuid」的独立提示 `[需真机验证]`（见 scope-review §4 承诺 a）。
- **支柱**：P1、P2。

### 阶段 3 · 通道协商（含能力协商）
> **顺序要求**：`mode` 能力协商必须在通道择优之前完成并冻结；协商未通过不得开始通道探测。理由：两套帧格式一旦进入同一条流即触发红线事故。

- **看到**：`[本冲刺待实现]` 三段式进度：「① 校验两端联机模式 → ② 选择通道 → ③ 建立连接」，每段有明确成功/失败态，不用无限转圈。
- **能操作**：取消（返回阶段 2）；`[本冲刺待实现]` 展开「诊断信息」（本机模式 / 对端模式 / 平台 / 版本 / 房号 / 通道 / 近 3 秒有效帧率）。
- **系统反馈**：
  - 能力协商通过 → `[已实现]` 状态栏「联机模式协商通过：A（…，2 人房）」（`CloudLink.cpp:2920-2923`）→ 进入通道探测。
  - **能力协商失败 → `[已实现]` 走 `fail()` → 大厅状态栏 + `%TEMP%/mgba_lobby_debug.log`，文案前缀「【联机模式协商失败】」，不进入通道探测、不自动重试、不自动切到另一端模式**（§5.1 / §5.2 候选 A）。
  - 通道探测：`[已实现]` 三通道自动择优、P2P 握手打洞成功显示「直连加速已启用」（`安卓版完整使用教程.md:88`）；`[本冲刺待实现]` 每次通道变化都回显实际生效通道与帧率（§7）。
- **状态**：三通道择优与「直连加速已启用」/ `mode` 协商位与 fail 逻辑 / 协商通过与失败文案 `[已实现]`（§2.1 F1/F4/F6/F7）；**但教程所述通道顺序与架构相反，见 §7.1 与 scope-review §4 承诺 g**；三段式进度与模式徽标 `[本冲刺待实现]`；打洞成功率与真机延迟 `[需真机验证]`。
- **支柱**：P2。

### 阶段 4 · 连接建立
- **看到**：状态栏「云端联机已连接，你是 1P（…）」（`MEMORY.md:56` 有实跑文案）；`[本冲刺待实现]` 常驻三件套徽标：**模式 + 通道 + 有效帧率**。
- **能操作**：进入游戏内的联机房间；`[已实现]` 联机倍速 `0.5x/1x/2x/4x`（PC `Tools → Speed`，Android「联机倍速」）。
- **系统反馈**：
  - **path A（默认）**：`[本冲刺待实现]` 明确告知「本模式不交换即时存档，两台设备各跑各的进度，游戏内联机线实时同步」——因为 path A 每端 1 核、无镜像核，且 `maybeSendInitialState()` 已加 `!m_officialMode` 门控（`2026-11-15.md:196-201`）。
  - `【path B 分支】`：连上互发一次即时存档给对端**隐藏镜像核**、载入后不复位、不覆盖可见核屏幕进度（`2026-11-15.md:3-12`；`安卓版完整使用教程.md:85`）；`[本冲刺待实现]` 在状态栏标注「兼容模式 · 4 人房」。
- **状态**：连接文案 / 倍速广播 `[已实现]`；三件套徽标 / 分模式存档说明 / path B 房型标注 `[本冲刺待实现]`；type 6 载入不复位与失败断链的用户可见表现 `[需真机验证]`（AC1–AC6 零自动断言，T-06 §3.1）。

## 5. 能力协商失败 · 完整交互（本文件核心）

### 5.1 触发条件与已落地的呈现通道

- **触发**：`type 1` / WSS hello-accept 携带的 `mode` 能力位在两端声明且不同（A/B）、能力位畸形、或对端未声明（旧客户端 / 官方 APK）。`resolveLinkMode()` 的 AUTO 默认已落地为 **2P→A、3/4P→B**（§2.1 F1）。
- **呈现通道（已落地，须以此为准）**：`fail()` 置 `m_closed`、`emit remoteKeys(0)`，然后 `status(text)` → **大厅状态栏** + `%TEMP%/mgba_lobby_debug.log`（`CloudLink.cpp:2819-2832`）。**当前实现没有模态对话框**；下文 S3 的对话框是设计侧的后续 UX 增强建议，不是现状。
- **文案前缀固定**：所有协商失败提示以「**【联机模式协商失败】**」开头，列本机/对端模式名与改法（§2.1 F4）。
- **必须直接 fail + 断链 + 玩家可见提示，禁止静默降级、禁止热切换帧格式**（T-06 §4.1 / §4.5 第 1 条；`CloudLink.cpp:2834-2841` C0 注释；`MEMORY.md:25`）。显式 A/B 不一致**永远 fail**，回落许可不覆盖该分支（§2.1 F6）。
- **iOS 加入 2P 房间（已裁定，主理人决策 4-A，见 scope-review §6 决策 4）**：AUTO 把 2P 房判为 A，而 iOS 完全没有 path A 且本轮红线禁止改 `ios/**`。⇒ iOS 设备加入 2P 默认 A 房间会触发**可见的「【联机模式协商失败】」而不是静默降级**，ADR 已列为 R3 / P0-11 未决。裁定口径：失败文案**指名 iOS 与「暂不支持 2P」**，保留这条可见失败提示；同时**隐藏「改用兼容模式」入口**，不给无效希望。
- **原「开箱即失败且无法自救」改写为三段式（主理人裁定口径）**：
  - **PC 侧已可自救**：AUTO 默认（F1）＋ 大厅「联机模式」下拉框（QSettings `link_mode`，F2），玩家有界面照做失败文案里的改法。
  - **Android 侧仅 ADB 广播可达**：`GBOY_LINK_MODE` 写入 `gboy_link_mode`（F3），但**仍无 UI 复选框**，普通玩家在界面上改不了模式 —— 这就是设计侧强保留意见的第一项。故 §5.3 的「自救」对 Android 普通用户**尚不成立**，需靠决策 1-A 的「分平台可执行步骤 + 一键复制命令」把 ADB 命令送到玩家手上。
  - **iOS 侧仍会可见失败**：无 path A、本轮禁止改 `ios/**`，AUTO 判 2P 为 A ⇒ 触发可见的「【联机模式协商失败】」而非静默降级（ADR R3 / P0-11），对应决策 4-A「明确 iOS 暂不支持双人联机 + 隐藏『改用兼容模式』入口」。
  - ⇒ 本节不再按「默认态」规格处理，改按「**明确的异常分支**」处理；「开箱即失败」仅对 iOS 组合与未声明对端成立。

> **非预期降级（新缺陷，已指派 T-03 修 main 侧）**：`GBoyLinkSession.onFrameBody` 的 `case TYPE_STATE` 无条件把 `stateOf(body)` 派发给 `events.onState`，path A 借壳的裸 20 字节包会被当成空 blob，触发 `EmulatorActivity.close()` **误断链**（`GBoyLinkSession.java:288-290`）。设计侧定性：这是**非预期降级行为 / 缺陷**，不是玩家可选路径，**不得**写成阶段 7「断线 → 重连」的正常旅程分支；玩家侧应看到的是「连接异常结束」，且修复前不得引导玩家去点「重新连接中继」。已列入 scope-review §5 风险 R9。

> - **PC 侧已解除**（大厅下拉框，QSettings 持久化 `link_mode`）；
> - **Android 侧仍成立**（仅 ADB 广播可达，无 UI 复选框，普通玩家没有界面能照做）—— 由**决策 1-A（已裁定）**的「分平台可执行步骤 + 一键复制命令」兜底，不新增产品代码；
> - **iOS 侧仍会可见失败**（决策 4-A，已裁定）。
> 本冲刺**不再需要**新增「一键与对端对齐」按钮来兜底；原 scope-review §6 决策 1 已改写为「呈现层是否要补对话框/说明卡」并由主理人裁定采纳 A，见 scope-review §6。

### 5.4 是否允许回落 B —— 以已落地实现为准

**结论：只有一条合法的回落路径，且不是「玩家可选地退回 path B」，而是「对端未声明模式时、经显式许可的兼容互通」。**

已落地规则（`CloudLink.cpp:2925-2941`、`GBoyCloudLink.java:2704-2719`）：
1. **适用范围极窄**：仅当 `peer == LINK_MODE_UNKNOWN`（旧客户端 / 官方 APK **没有能力位**）。两端都已声明且不一致 → **永远 fail，不回落**（F6）。
2. **必须显式许可**：PC `MGBAX_LINK_ALLOW_LEGACY=1`；Android ADB `allow_legacy=true`。默认关闭，`m_allowLegacyPeer` 初始 false（`CloudLink.cpp:644`）。
3. **不是静默降级**：状态栏明确打「**警告：对端未声明联机模式…按 … 显式许可回落为 B…此路径未经 2P 云端验收，不建议用于交付**」。玩家可见、措辞带风险告知。
4. **不允许热切换**：绑定发生在任何游戏帧之前（`negotiateLinkMode()`），连接存活期间不切帧格式。
5. **对准硬约束**：`CloudLink.cpp:2834-2841` C0 注释写明「绝不挑一个『能跑的』静默降级」。

**设计侧后续建议（未落地，不得描述为现状）**：若下一冲刺要把这条路径产品化，需补 §6.4 的落差告知卡（4 人房 / 两端各跑一局 / 帧率更低 / 实验性且不计成绩）+ 双端各自确认 + 状态栏常驻「兼容模式（实验性）」徽标。**在补齐前，本文件不把「玩家显式发起 → 双端确认 → 重建」写成现行行为**。

**iOS 组合**：iOS 无 path A，AUTO 判 2P 为 A ⇒ iOS 加入 2P 房走的是**显式不一致 → fail**（若 iOS 声明了 B）或**未声明 → 默认 fail**（无 `allow_legacy` 时），**都不是「回落 B 就能玩」**。T-06 §5.1 明确 iOS 2P 不可用。失败文案须指名 iOS 并给「暂不支持 2P」，不得给无效希望；取舍见 scope-review §6 决策 4。

**与「通道级自动回退」的边界**：本节的 mode 回落属架构级，仅显式许可且仅对未声明对端生效；§7 的 P2P→隧道属通道级，允许自动但必须可见。两者不可共用同一套文案或同一套降级开关。

## 6. path B 的体验落差 · 自我决定论 / 心流分析与缓解

### 6.1 落差定义
玩家点击的是「双人联机 / 2P」，心理契约是 **1v1 真人对真人**；实际拿到的是「本机 4 核 + 网络只传按键」的 **4 人房，2 真人（slot1/2）+ 2 NPC 占位（slot3/4）**，且**两台设备各跑一局独立的 4 人房**，一致性靠同 ROM + 同存档 + 同按键序列 + 帧级相位维持（`2026-11-15.md:97-100`）。这不是「画面里多了两个角色」，是**对局本体与对手本体被替换**。

### 6.2 自我决定论三要素（Deci & Ryan）受影响分析

| 要素 | 玩家期待 | path B 实际 | 受损机制 | 严重度 |
| --- | --- | --- | --- | --- |
| **自主 Autonomy** | 我选择「和某个真人打一场」 | 4 个席位里 2 个由系统填充；导航期 NPC 由柜台对话状态机接管、进对战键源恒 0；且模式若由系统「自动切」则连模式都不是我选的 | 玩家对「和谁打、打几人、怎么开始」的因果控制被系统代管；最伤的是**事后才发现** | 高 |
| **胜任 Competence** | 输赢归因清晰：我操作好/差 | NPC 恒 0 键改变了对战难度与结果归因；有效帧率可能从 ~60 fps 掉到 4.6~4.9 fps，按键→画面反馈延迟被拉长，操作失误被误读为「我手残」 | 反馈延迟与结果归因污染同时削弱「我能打好」的感知；「卡」被归因为自己而非系统 | 高 |
| **关联 Relatedness** | 屏幕对面是一个具体的人 | 两端各跑独立 4 人房，对端真人并不真的在同一局里；一旦帧级相位漂移，画面分叉，玩家会意识到「对方其实不在我的房间」 | 联机的核心动机（与真人共处一局）被揭示为模拟；这是**信任级**损伤，不是体验级 | **最高** |

### 6.3 心流（Csikszentmihalyi）影响
心流三条件在 path B 下同时被破坏：
- **明确目标**：从「击败对面那个真人」漂移到「陪 4 人房跑完流程」，目标边界模糊。
- **即时反馈**：帧率塌陷（60 → 4.6~4.9 fps；跨公网帧锁步理论上限 0.7~1.5 fps 且物理不可行）使按键反馈不再即时，挑战—技能平衡无法建立。
- **挑战—技能匹配**：导航期状态机代管＝玩家无事可做（无聊区）；对战中低帧率＋NPC 干扰＝不可控（焦虑区）；能力协商失败/断链＝反复中断。玩家在**无聊与焦虑之间来回，落不进心流通道**。
- 设计含义：path B **不适合作为默认路径，也不适合作为「自动回退」的结果**；它只能作为玩家知情后主动选择的兼容形态（P1/P2）。

### 6.4 产品侧缓解方案（命名 / 界面 / 标注）

| # | 措施 | 具体做法 | 状态 |
| --- | --- | --- | --- |
| M1 | **改名，停止叫「双人联机 2P」** | path A 保留产品名「**双人直连**」；path B 统一改称「**兼容模式（实验性）· 2 真人 + 2 电脑占位**」。所有 UI、状态栏、失败文案、教程改写建议统一使用这两个名字 | `[本冲刺待实现]` |
| M2 | **进房前一次性说明卡（S6）** | 「此模式为兼容实验：两端各自运行一局 4 人房，另两个席位由电脑占位、不会操作；它不等于 1v1 对战，帧率可能低于直连。」+ `[我了解，继续]` / `[返回]`；每次进入显示，不允许「不再提示」 | `[本冲刺待实现]` |

| M7 | **对端真人可感知** | 在 S4/S8 显示对端昵称与连接质量，强化「确实有一个真人在另一端」，部分补偿 Relatedness | `[本冲刺待实现]` |

> 设计侧保留意见：M1–M7 是**缓解**而非「解决」。只要 path B 仍是「两端各跑一局」，Relatedness 的落差就无法靠文案消除。本文件不推翻架构，但把这一点记为**已知产品债**，见 scope-review §5 风险 R3。

## 7. 通道降级与帧率提示

### 7.1 顺序口径
本规格按**已定架构**描述：path A **P2P 直连优先**，打不通回落到 UDP 中继 / 服务器隧道。教程现写的是「UDP 中继 → 服务器隧道 → P2P 直连」且把 P2P 表述为「握手后打洞的加速」（`安卓版完整使用教程.md:88`、`PC版完整使用教程.md:108`），**顺序与架构相反**；设计侧不改实现，只要求「实际生效的通道」如实回显，并把顺序冲突列为教程改写项（scope-review §4 承诺 g）。

### 7.2 玩家必须理解的因果
> 「不是游戏卡了，也不是倍速没调一致 —— 是直连没打通，现在走的是服务器隧道，所以画面变慢了。」

这句是本节全部文案的核心。教程原句「这是联机卡的最常见原因，不是网络问题」（`安卓版完整使用教程.md:112`、`PC版完整使用教程.md:114`）在本冲刺起**需要补充例外**：通道回退同样会造成卡顿，且是可从状态栏直接判定的。

### 7.3 有效帧率定义与阈值（公式，标变量与单位）

```
变量：
  N        = 采样窗内实际渲染帧数（单位：帧）
  W        = 采样窗时长，W = 3 s（单位：秒）
  F_eff    = 有效帧率 = N / W（单位：fps，帧/秒）
  T_hold   = 状态切换去抖时长 = 2W = 6 s（单位：秒）

分档判定（连续 2 个采样窗同档才切换文案，避免闪烁）：
  GREEN   : F_eff ≥ 50 fps           → 直连 / 高质量通道
  YELLOW  : 10 fps ≤ F_eff < 50 fps  → 通道降级，可玩但有延迟
  RED     : F_eff < 10 fps           → 通道受限，不建议对战
  BLOCKED : 通道 = 跨公网帧锁步      → 理论上限 0.7~1.5 fps，物理不可行，
                                        不建立对战，直接提示「此通道不可用于联机对战」
```

**阈值来源与 caveat（不臆造）**

| 数值 | 来源 | 说明 |
| --- | --- | --- |
| ~60 fps | `GBoy联机实现拆解与移植方案.md:362-363`（P2P 直连两端各 1 核进 `BattleMainCB2`、60 fps）；`§7.6` | 已实测，但为 PC/双端直连场景，`[需真机验证]` |
| 4.6~4.9 fps | `MEMORY.md:30-31`、`2026-11-15.md:166-167`；T-06 §5.1 第 4 条 | 工程来源是 **Android native 无 `sioFastFrame` 等价实现**；任务口径把它对应到「P2P 打不通回隧道」的玩家可见表现。**PC/Qt 有 `sioFastFrame`，同通道帧率可能不同** ⇒ 阈值须按端分别真机校准 |
| 0.7~1.5 fps | `GBoy联机实现拆解与移植方案.md:305-309`；`MEMORY.md:94` | 跨公网帧锁步理论上限，属 path B 且物理不可行，本冲刺**不提供**该通道 |
| 50 / 10 fps 阈值 | 本规格设计侧建议值 | 非工程实测，属**待校准参数**；与 T-06 §4.4「帧率跌破可玩阈值」呼应，建议把「可玩阈值」定为 `F_eff < 10 fps` 持续 6 s |

### 7.4 状态栏文案（S4 / S5）

| 档 | 常驻状态栏文案 | 首次切换时一次性说明条（S5） | 玩家动作 |
| --- | --- | --- | --- |
| GREEN | `双人直连 · 直连加速已启用 · 约 60 fps` | —（不打扰） | 正常游玩 |
| YELLOW | `双人直连 · 服务器隧道 · 约 X fps，操作可能有延迟` | 「直连没打通，已自动改用服务器隧道。画面变慢是通道造成的，不是游戏卡了，也不是倍速问题。」 | `[了解原因]` `[重新连接中继]` |
| RED | `⚠ 通道受限 · 约 5 fps · 不建议对战` | 「当前通道约 5 fps，操作会明显延迟。建议重新连接中继重试直连，或换网络后重连；继续对战体验较差。」 | `[重新连接中继]` `[退出联机]` `[了解原因]` |
| BLOCKED | `此通道不可用于联机对战` | 「跨公网帧锁步每帧需要多次往返，物理上无法达到可玩帧率。请改用直连/中继通道。」 | `[返回大厅]` |

**文案约束**
- 颜色**不得作为唯一编码**：三档同时带文字 + 图标（● / ▲ / ⚠），见 §9。
- 帧率显示用**约数**（「约 5 fps」），不显示精确小数，避免玩家把 4.6 与 4.9 的抖动误读为系统不稳定。
- 不得写「加速中 / 优化中 / 正在为你切换」等掩盖降级的正向措辞。
- 从 GREEN 掉到 RED 时，说明条只弹**一次**（同一连接内），不重复打断对战。
- 若 `F_eff` 低但通道显示 GREEN（例如 Android native 缺 `sioFastFrame`），以 **F_eff 实测为准**判档，通道徽标保留但附加「本机性能受限」；此项 `[需真机验证]`，因为 PC 与 Android 的归因不同。

### 7.5 与既有「倍速拉扯」提示的关系
`[已实现]` 的「一边 1x 一边 4x 会拉扯…不是网络问题」（`安卓版完整使用教程.md:112`）保留，但**必须补一句**：「若状态栏显示『服务器隧道 / 通道受限』，则卡顿来自通道，请点『重新连接中继』，调倍速无效。」否则玩家会把通道降级误判为倍速问题，做无效操作（P2 受损）。改写文本见 scope-review §4 承诺 c。

**支柱漂移检查（设计理论红线）**
- **主导策略**：若「兼容模式（实验性）」比「双人直连」更容易连上（例如默认就是 B、或失败时一键切 B 无摩擦），玩家会**全部涌向 B**，path A 成为死路径、P1 被架空。⇒ **AUTO 默认 2P→A（F1）+ 显式不一致永远 fail（F6）+ M6「不默认、不自动」**构成结构性反主导策略；§5.4 的「仅显式许可、仅对未声明对端」窄回落也保留了摩擦。
- **认知过载**：一次性把 mode / 通道 / 帧率 / 核数 / NPC / type 6 全部塞给玩家会压垮 Submission。⇒ §9 分层披露。
- **经济失衡**：不适用（本功能无资源经济/掉落/进度曲线）。但**进度守恒**是等价物：M-6/M-7/M-8 必须保证联机不吞掉玩家存档进度。
- **支柱漂移**：把 path B 当「双人联机」卖、把通道回退说成「加速」、把静默降级包装成「智能优化」——三者分别漂移 P1/P2/P2，已在 §1 与 §6.4 标注并给出对应文案约束。

## 9. 可访问性与认知负荷（分层披露）

> 正式 `design/accessibility-requirements.md` 缺失，以下按通用基线给出，待文档补齐后复核。

1. **分层披露（防认知过载）**
   - L1 默认可见：模式徽标 + 通道 + 帧率档 + 倍速档（S4），**仅 4 项**。
   - L2 一次性：降级说明条（S5）、path B 说明卡（S6）、失败对话框（S3）。
   - L3 折叠/高级：诊断信息、RTT、`mode` 值、房号、版本号、ADB/环境变量自救步骤。
   - 禁止在 L1 出现 path A/B、SIO、type 6、核数、帧格式等内部术语。
2. **颜色非唯一编码**：GREEN/YELLOW/RED 必须同时有文字标签与图形符号（● / ▲ / ⚠）；色盲模式下文案仍完整可读。
3. **动效**：帧率徽标变化用淡入不用闪烁；去抖 `T_hold = 6 s` 同时服务于光敏与防抖动。
4. **读屏 / 键盘**：S3 四个按钮有确定焦点顺序与可朗读标签；失败对话框不自动消失、不靠超时关闭。
5. **文案可读性**：主文案句长 ≤ 30 字、避免英文缩写；`fps` 首次出现写「帧/秒（fps）」。
6. **窄屏**：手机端采用文案 C 的精简版，但**不得删掉「进度未受影响」与「如何统一模式」**。
