### 本轮证据更新（覆盖任务下发时的旧描述）

1. **本机诊断腿已进对战，但跨设备云端 2P 仍未闭环**。T-03 单变量 A/B 证实 `busgame-lockstep` 的 `BATTLE=NO / 080B2EED` 是**判据地址窗口过期造成的假阴性**：`/d/gen8/rom.gba` 被并发会话重编译后代码整体平移 `0x16E64`，而 `gboylink_test.cpp:2693-2700` 写死旧 ROM 区间；旧 ROM 腿实跑 `BATTLE=YES / 0809AFCD / battleSamples=3387`。⇒ 凡本文件写「核心循环未验证 / 进对战闭环」处，一律改按「本机诊断腿已进对战、跨设备云端 2P 仍未闭环」理解；两者不是一回事。
2. **AUTO 默认已落地**：2P→A、3/4P→B，`resolveLinkMode(playerCount)` **PC / Android 同逻辑**（`CloudLink.cpp:2855-2861`、`GBoyCloudLink.java:2651-2656`）。⇒ 任务下发时「PC 默认 A / Android 默认 B」的硬编码分叉**已过时**，这一条开箱即失败的前提已消除。
3. **自救路径分平台落地，但只解决了一半**（主理人本轮修正，覆盖我上一轮「两条已解除」的过度结论）：
   - **PC 侧已可自救**：大厅「联机模式：AUTO / A / B」下拉框，QSettings 持久化 `link_mode`（`LobbyView.cpp:89-117,291-297`）。
   - **Android 侧仅 ADB 广播可达**：`GBOY_LINK_MODE --es mode A|B|AUTO` 写入 SharedPreferences `gboy_link_mode`（`EmulatorActivity.java:5533-5591,5575-5598`），但**仍无 UI 复选框 / 下拉框**（`showLinkDialog():5275+` 无该控件）⇒ 「普通玩家没有界面能照做」**现在只对 Android 侧成立**。
   - **iOS 侧仍会可见失败**：无 path A、本轮红线禁止改 `ios/**` ⇒ 加入 2P 默认 A 房间触发可见的「【联机模式协商失败】」而非静默降级（ADR R3 / P0-11）。
   - ⇒ 正确表述为「**PC 侧已可自救、Android 侧仅 ADB 广播可达、iOS 侧仍会可见失败**」，不再是笼统的「开箱即失败且无法自救」，也不是笼统的「已解除」。
4. **能力协商失败文案已落地且以代码为准**：`fail()` → 大厅状态栏 + `%TEMP%/mgba_lobby_debug.log`，前缀「**【联机模式协商失败】**」；仅 `MGBAX_LINK_ALLOW_LEGACY=1`（PC）/ `allow_legacy=true`（Android ADB）且**对端未声明**时才显式回落 B，状态栏打「警告…显式许可回落…不建议用于交付」；显式 A/B 不一致**永远 fail**（`CloudLink.cpp:2819-2832,2925-2948`；Android `GBoyCloudLink.java:2665-2726`）。T-06 §4.1 的旧建议文案与落地字符串不同，以代码为准。
5. **新增缺陷**：`GBoyLinkSession.onFrameBody` 的 `case TYPE_STATE` 无条件派发空 blob，path A 借壳包触发 `EmulatorActivity.close()` 误断链（`GBoyLinkSession.java:288-290`，已指派 T-03 修 main 侧）。设计定性 = **非预期降级行为**，非玩家可选路径，不并入正常旅程（§5 R9）。

### 判 CONCERNS 的理由（按新证据重列）

**支持「不判 FAIL」的三点**
1. 架构方向清晰且本轮不推翻：2P 首选 path A、type 6 并存 + `mode` 能力协商隔离、iOS 只支持 path B；且 **C0 能力协商 / AUTO 默认 / 失败文案已由 T-03 落地**，设计侧可据此产出完整 UX 规格（`2p-link-ux-spec.md`）。
2. 范围边界可界定：本冲刺「该做 / 延后 / 明确不做」逐条列清（§2、§3），不存在「设计无法评审」情形。
3. 剩余缺口（AC1–AC6 断言、教程改写、真机验证、呈现层 UX 化、Android 可达性）分别归属 T-04 / T-06 / 真机 Playtest / 已裁定决策 1-A / 决策 4-A 落地，属跨线依赖；**四项产品决策已由主理人裁定完毕**（§6），不再有「待拍板」阻塞。
4. **设计侧判定维持 CONCERNS**（主理人本轮确认）：AUTO 默认与 PC 下拉框落地消除了「PC 默认 A / Android 默认 B」这一条，但 Android 普通用户可达性与 iOS 平台告知两项仍在，不足以转 PASS。

**支持「不判 PASS」的六点（CONCERNS 的实质）**
1. **Android 普通用户可达路径未闭环**（强保留意见第一项）：Android 改模式**仅 ADB 广播可达、无 UI 复选框**，普通玩家在界面上照做不了失败文案里的「请两端设置相同的联机模式」。由**决策 1-A（已裁定）**的「S3 内分平台可执行步骤 + 一键复制命令」兜底，零新增产品代码；该说明文本尚待落地验收。
2. **iOS 平台告知未闭环**（强保留意见第二项）：AUTO 把 2P 判为 A，iOS 无 path A 且本轮红线禁止改 `ios/**` ⇒ iOS 加入 2P 默认 A 房间触发**可见的「【联机模式协商失败】」而非静默降级**（ADR R3 / P0-11）。**决策 4-A（已裁定）**：明确「iOS 暂不支持双人联机」+ 隐藏「改用兼容模式」入口；平台提示与失败文案尚待落地。
3. **非预期降级缺陷未修**：`case TYPE_STATE` 误断链（§5 R9），玩家会看到无声断线；属缺陷而非旅程分支。
4. **产品承诺与架构已脱节**：至少 3 句教程原文不成立（§4），尤其「连上互发一次即时存档给隐藏核」是 **path B 专属**，2P 首选 path A 无镜像核、明确不发整份 savestate。该跨文档口径分裂已由主理人受理并中转 T-04 / T-06，设计侧不改其它文档。
5. **帧率阈值缺真机数据**：60 fps / 4.6~4.9 fps / 0.7~1.5 fps 来源与归因不同，PC 与 Android 不同源；阈值是设计侧建议值（决策 3-A 已裁定采用），未经真机校准。
6. **呈现层未 UX 化**：模式徽标、三段式协商进度、状态栏通道/帧率三件套、通道降级归因句仍待实现；功能不缺，但玩家「看得懂」尚未闭环。

**设计侧强保留意见（保留，按主理人指令收窄为两项）**
> 2P 云端交付门 FAIL 与跨设备未闭环的结论**不因本机诊断腿 `BATTLE=YES` 而松动**；单腿绿灯与 `6/6 PASS` 均不构成放行依据。设计侧建议：在①**Android 普通用户可达路径**（决策 1-A 的分平台步骤 / 一键复制命令落地并验收）与②**iOS 平台告知**（决策 4-A 的「iOS 暂不支持双人联机」提示 + 隐藏入口落地）两项闭环、且跨设备 E2E 有落盘证据（T-06 §3.6 / F19 判据）之前，**不以「2P 可用」口径对外交付**；可不阻断代码合入与内部验证。

### 3.2 四项特别判断（逐条明确结论）

#### 判断 1 · iOS 2P 支持 → **已裁定（主理人，决策 4-A）；本冲刺不做功能，只做「可见告知」**

- **新事实（本轮收口口径）**：T-03 已实现 **AUTO 默认「2P→A、3/4P→B」**；iOS 完全没有 path A，且本轮红线**禁止改 `ios/**`**。⇒ **iOS 设备加入 2P 默认 A 房间会触发可见的「【联机模式协商失败】」而不是静默降级**，ADR 已列为 **R3 / P0-11 未决**。设计侧确认：这是「可见失败」而非「静默降级」，符合 P2 硬约束，但**产品上是一个明确的不可用缺口**，必须对外讲清。
- **已裁定（主理人，决策 4-A）**：明确「**iOS 暂不支持双人联机**」+ **隐藏「改用兼容模式」入口**；不隐藏 iOS 组合本身的可见失败提示，但不给「改用兼容模式继续」的无效希望。对应 §6 决策 4 的选项 ③ / 裁定 A。
- **本冲刺该做**：S1 平台提示「当前 2P 仅 PC ↔ Android 可用，iOS 暂不支持双人联机」；协商失败文案指名 iOS 与「暂不支持 2P」（`ux-spec.md` §5.1、§5.4、§10 U8 / U4b）；教程侧同等口径由 T-06 §5.2 A/B/C 落地。
- **理由**：不告知 → 用户按教程「手机和 PC 能互连」操作必失败（T-06 R3）；做功能 → 超出本冲刺真机/编译能力、且红线禁止改 `ios/**`。
- **不承诺下一冲刺**：仅列为延后候选，取决于 macOS + Xcode 真机与 path A 先在 PC↔Android 闭环。

#### 判断 2 · NPC 队伍表现定义 → **本冲刺只做「最小可见定义」，角色化表现延后 / 倾向不做**

- **本冲刺该做（最小定义，且是设计侧关键判断）**：把 slot3/4 定义为**「占位符」而非「角色」**。具体落到四条玩家可见规则：
  1. 席位标注为 `3P、4P 电脑占位（不操作）`，灰显，禁止用默认玩家名或空白名让 NPC 看起来像真人（P1）；
  2. 对战中键源恒 0、导航期由柜台对话状态机接管、进对战释放（`2026-11-15.md:100-101`）；
  3. 说明卡明示「两端各跑一局独立的 4 人房」；
  4. 该模式不计入任何胜负/成就/排行统计。
- **设计结论**：**「NPC 队伍表现」这个概念应当被消除，而不是被设计**。一旦给占位符配队伍、AI、台词，就等于承认它是「第三个玩家」，会与 P1「两个真人各自一台」正面冲突，并把兼容形态包装成多人内容 —— 属支柱漂移。故本冲刺不定义队伍，D2 延后且倾向明确不做。
- **理由**：范围收敛 + 避免主导策略/难度失衡 + 无真机数据可校准。

#### 判断 3 · UI 开关暴露到什么程度 → **分平台结论：PC 有 UI 下拉框，Android 仍无 UI 复选框；设计侧接受现状，本冲刺补「结果可见层」**

- **已落地（接受，不再建议新增控制层）**：**PC** 大厅「联机模式」下拉框 `AUTO / A / B`，QSettings 持久化 `link_mode`（`LobbyView.cpp:89-117,291-297`）；**Android 仅** `GBOY_LINK_MODE` ADB 广播写入 SharedPreferences `gboy_link_mode`（`EmulatorActivity.java:5533-5591,5575-5598`），**无 UI 复选框 / 下拉框**（`showLinkDialog():5275+` 无该控件）；`MGBAX_LINK_MODE` 环境变量覆盖。⇒ 任务下发时「不暴露模式控制层」的判断**只在 PC 侧被推翻**，Android 侧仍成立；设计侧**不推翻架构、按现状适配**。
- **设计侧对现状的评价**：默认 AUTO（2P→A、PC/Android 同逻辑）已把「玩家手动制造不一致」的概率压到最低；显式 A/B 入口配合「不一致即 fail」硬约束，不构成静默降级。故接受，仅建议：① PC 下拉框选项里的工程术语（`每端 1 核 + SIO 包中继`）后续打磨时柔化为产品名（本轮不改代码）；② 默认值必须是 AUTO，不得预选 B。
- **本冲刺该补（结果可见层）**：S1 只读模式徽标 + 平台可用性提示 + 预防性黄条；S3 失败提示 UI 化（可选，决策 1-A 已裁定）；S4 HUD 状态栏模式 + 通道 + 有效帧率 + 倍速档（L1 仅 4 项）；S6 path B 说明卡；S5 降级说明条；S8 席位标注。
- **「死路」按平台分列（取代上一轮「已解除」的过度结论）**：**PC 侧已解除**（下拉框玩家能照做）；**Android 侧仍成立**（仅 ADB 可达、无 UI 复选框，普通玩家没有界面能照做）—— 这是设计侧强保留意见第一项，由**决策 1-A（已裁定）**的「S3 内分平台可执行步骤 + 一键复制命令」兜底，零新增产品代码；**iOS 侧仍会可见失败**（决策 4-A，已裁定）。
- **理由**：控制层已存在且约束完备，再新增「一键对齐」会制造更多不一致与认知过载；Android 的缺口用「把 ADB 命令送到玩家手上」而非新增 UI 控件来补，符合零新增产品代码的裁定前提。分层披露规则见 `ux-spec.md` §9。

#### 判断 4 · 2 人局域网是否要补界面 → **不补，延后；本冲刺只保留明确声明**

- **结论**：维持 `安卓版完整使用教程.md:98`「2 人局域网没有界面，只能用 ADB 广播」的现状。
- **理由**：
  1. 主路径是云端房间 2P；2 人局域网的现有唯一入口 `io.mgba.android.action.GBOY_LOCAL_LINK --ez host true --ei players 2` 是**调试/自动化向**，且 T-06 §5.1 #2 明确其**零自动断言覆盖**；
  2. 补 UI 等于新增第 4 条联机路径，与本冲刺「能力协商隔离 / 收敛口径」的方向相反，会把测试面从 3 通道 × 2 mode 再乘一条；
  3. 本冲刺连云端 2P 都尚未闭环（D7），在优先级上不应先做边缘路径的界面；
  4. `§7.6:362-363` 的「P2P 直连两端各 1 核 → 60 fps」是 path A 的既有证据，说明**两人直连能力本身存在**，缺的只是图形入口，属体验增强而非功能缺口。
- **延后条件**：先补 2P 局域网的自动断言，再评估 UI；且需同步定义该路径的 `mode` 归属（走 A 还是 B），否则又是一处不一致。

#### 承诺 a · 两边同一个 ROM（安卓 `:70` / PC `:82` / PC `:210`）

**问题**：`MEMORY.md:52-55`、`2026-11-13.md:380-386` 记录云端大厅按 `uuid = "BPEE,"+ROM md5` 派发，两端跑逐字节相同的 `rom.gba` ⇒ 同一 uuid ⇒ 服务器把两端当成同一个玩家、消息只回显给自己（`"self":true`），对端永远收不到；已验证修法是给一端 ROM 尾部补 1 字节填充（改变 md5，不改游戏内容）并配套单独 `.sav`。教程「内容必须一致 / 不同 dump 都算不同游戏」既可能被读成「必须逐字节相同」，又与「必须让 md5 不同」张力明显；且「大厅会比对指纹」比的是游戏指纹还是整文件 md5，口径需工程确认。

**建议改写文本（替换安卓 `:70`）**：

```
1. **两边必须是同一个游戏**（同版本、同语言、同 dump；不同汉化 / 不同版本会被判成不同游戏）。

   两端文件一模一样时会被当成同一个人，消息只回显给自己、对端收不到。
   做法：给其中一端的 ROM 尾部补 1 字节填充（不影响游戏内容），并给它配一份单独的 `.sav`。
```

**建议改写文本（替换 PC `:82`，与 `:210` 联动）**：

```
1. **两边必须是同一个游戏**（同版本、同 dump；大厅会比对游戏指纹，不同汉化 / 不同版本报「两边的游戏不一致」）。
```

**建议改写文本（替换安卓 `:88`）**：

```
通道会**优先尝试 P2P 直连**（握手后打洞，成功显示「直连加速已启用」，约 60 fps）；
打不通时自动回落到 UDP 中继 / 服务器隧道，**不会中断连接、也不会弹错误**。

强制只走隧道设 `MGBAX_NO_DIRECT=1`（调试用，会更慢）。
```

**建议改写文本（替换 PC `:108`）**：


### 决策 1 · 失败提示的「呈现层」是否 UX 化 —— **已裁定（主理人）· A**

> 前提变化：AUTO 默认 + PC 下拉框 + Android ADB 入口已落地，`fail()` 也已给状态栏 + 调试日志与「【联机模式协商失败】」文案。⇒ 原决策从「是否补自救路径、否则死路」改写为「是否把已落地的状态栏文案再做一层 UI 呈现」。
> **裁定补充（主理人本轮修正）**：Android 侧「仅 ADB 广播可达、无 UI 复选框」**仍成立**，普通玩家没有界面能照做 ⇒ 「自救路径」并未全面解除，只是 PC 侧解除。故采纳 A 时 S3 的分平台步骤必须**给出可直接一键复制的 ADB 命令**，这是 Android 普通用户可达路径的兜底，属强保留意见第一项的闭环动作；不新增 Android UI 复选框（超出本冲刺、需改 `android/**`）。

| 选项 | 内容 | 代价 / 评价 |
| --- | --- | --- |
| **A（已裁定 · 主理人采纳）** | **沿用已落地状态栏文案，零改动**；S3 内补一份「如何统一模式」的**分平台可执行步骤 + 一键复制命令**（PC 指下拉框 / Android 给可直接复制的 ADB 命令） | **裁定采纳**：零新增产品代码、与 T-03 字符串逐字一致、不绕过人工审批；Android 可达性由此兜底 |
| B | 在 A 之上把同一文案 UI 化为对话框 + 动作按钮（复制诊断 / 返回 / 查看改法） | 未采纳；可读性最好，但需 T-03 补 UI 接线与断言，属下一冲刺呈现层增强 |
| C | 新增显式「一键与对端对齐」按钮（双端确认 → 断链 Drain → 重建握手） | **未采纳**：可能被理解为「放宽不一致即 fail」，且控制层已够用，再加控制项会制造更多不一致与认知过载 |

**已裁定（主理人）采纳 A**：失败后 S3 内给分平台可执行步骤 + 一键复制命令，零新增产品代码。

### 决策 4 · iOS 2P 产品范围 —— **已裁定（主理人）· A（= 推荐项 ③）**

> **新事实**：T-03 已实现 AUTO 默认「**2P→A、3/4P→B**」；iOS 完全没有 path A，且本轮红线禁止改 `ios/**`。⇒ **iOS 设备加入 2P 默认 A 房间会触发可见的「【联机模式协商失败】」而不是静默降级**。这是符合硬约束的可见失败，但产品上是一个明确的不可用缺口。
> **裁定（主理人，决策 4-A）**：明确「**iOS 暂不支持双人联机**」+ **隐藏「改用兼容模式」入口**，等同本表推荐项 ③；不新增产品代码、不碰 `ios/**`、不绕过人工审批。

| 选项 | 内容 | 评价 |
| --- | --- | --- |
| **① 明确 iOS 只支持 path B**（未采纳） | 对外口径写「iOS 仅支持兼容模式（实验性）」；iOS 侧保持 B，2P 房间由其他端显式切 B 才能与 iOS 互通 | 与「iOS 只支持 path B」的默认假设一致，但会诱导玩家把 2P 房切到 B —— 而 path B 是 4 人房 + 2 NPC 占位、帧率更低、跨设备未闭环，等于把主路径推向最差体验；且与 T-06 §5.1 #1「iOS 2P 不可用」矛盾 |
| **② 补 path A 到 iOS**（未采纳） | 移植 SIO 分开控制桥与 `sioFastFrame` 等价实现，让 iOS 能进 2P 默认 A 房间 | 体验最完整，但 iOS 无 path A（`ios/mGBA/*.swift` grep 零命中）、仅过 `swiftc -parse`、需 macOS + Xcode 真机、CI #65 的 runtime check 从未执行；**本轮红线明确禁止改 `ios/**`**，成本与风险都超出本冲刺 |
| **③ 暂不开放 2P 给 iOS（已裁定 · 主理人采纳，即「决策 4-A」）** | 明确写「**iOS 暂不支持双人联机**」；iOS 加入 2P 默认 A 房间时给可见的「【联机模式协商失败】」并指名 iOS，**隐藏「改用兼容模式」入口**、不给无效希望；教程与 S1 平台提示同步；功能实现延后且不承诺下一冲刺 | 诚实、零新增代码、不碰 `ios/**`、与 T-06 §5.2 A/B/C 及 §5.1 #1 完全一致；代价是 iOS 用户在本冲刺确实玩不了 2P，但该事实本来就没被验证过可用 |

**已裁定（主理人）采纳 ③ / 决策 4-A**：明确「iOS 暂不支持双人联机」+ 隐藏「改用兼容模式」入口。
理由（三条）：① 本轮红线禁止改 `ios/**`，② 与 T-06 已定口径零冲突、可立即落地为可见文案，③ 把「未验证的不可用」如实讲清优于给一个会掉到 4 人房 + 低帧率的虚假希望 —— 后者会同时违反 P1（两个真人各自一台）与 P2（状态诚实）。① 会诱导主路径滑向 path B，属支柱漂移；② 属下一冲刺且需真机能力，本冲刺不具备。
配套动作：S1 平台提示、失败文案指名 iOS、隐藏「改用兼容模式」入口、`ux-spec.md` §10 U4b/U8 验收点、教程口径交 T-06 §5.2。
